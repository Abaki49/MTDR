## Known Issues & Blockers

### Python-level defaults not enforced at DB level
- `is_active`, `is_super_admin`, `visibility`, and `status` use Python-level `default=` not `server_default`.
- Any code path that inserts rows bypassing the ORM (raw SQL, bulk load) will get `NULL` instead of the intended default.
- **Impact:** Low for now (ORM-only codebase), but should be noted if raw SQL is ever introduced.

### Migration files generated inside container don't persist to host
- The `versions/` directory is **not** volume-mounted in `docker-compose.yml`.
- Running `alembic revision --autogenerate` inside the container creates the file only inside the container's filesystem.
- **Workaround:** Must manually copy the file out (e.g., `docker compose exec app cat ... > local_file.py`).
- **Fix:** Add a volume mount for `./app/database/migrations/versions/` in docker-compose.yml to sync automatically.

### No CHECK constraints on `memberships.status` or `resources.visibility`
- `status` accepts any string (not just `ACTIVE`/`SUSPENDED`/`INVITED`).
- `visibility` accepts any string (not just `PUBLIC`/`PRIVATE`).
- Validation relies entirely on the application layer. No DB-level guard against invalid data from direct SQL writes.

### Alembic env.py relies on sys.path hack
- `env.py` inserts parent directory into `sys.path` so `from app.core.config import settings` works.
- Works in the container but may cause import issues if alembic is run from a different working directory or context.
- **Impact:** Low inside Docker, but could break in local dev setups.

### Redis integration complete (BE-107)
- Redis 7 (alpine) runs as a separate service in docker-compose, health-checked before app starts.
- `redis.asyncio` client initialized in FastAPI lifespan and shared via module-level `redis_client`.
- `user:{id}:identity` cached with 5-minute TTL; served on cache hit, populated from DB on cache miss.
- `invalidate_user_cache(user_id)` available for manual/sync invalidation.

### Alembic requires running app container
- `alembic` commands run via `docker compose exec app alembic ...` — the app container must be up.
- This creates a circular-ish dependency: DB must be healthy → app can start → alembic can run.
- Fine for dev, but worth noting for CI/CD pipelines where migration execution order matters.

### Operational notes
- DB credentials are hardcoded in `docker-compose.yml` and `alembic.ini` (user: `mtdr`, password: `mtdr`, db: `mtdr`).
- `docker compose down -v` destroys all DB data (named volume `pgdata` is removed with `-v`).
- App container rebuild is required for any code change (`docker compose up --build -d app`).

## BE-103 — Implement Authentication Service

**Status:** Completed

### What was implemented
- **`app/core/config.py`** — Added JWT settings: `jwt_secret_key`, `jwt_algorithm` (HS256), `access_token_expire_minutes` (30), `refresh_token_expire_days` (7).
- **`app/core/security.py`** — Argon2 password hashing via `passlib.context` with `schemes=["argon2"]`.
- **`app/core/auth.py`** — JWT utilities (`create_access_token`, `create_refresh_token`, `decode_token`) and `get_current_user` FastAPI dependency.
- **`app/schemas/auth.py`** — Pydantic schemas: `LoginRequest`, `RefreshRequest`, `TokenResponse`, `UserResponse`, `MembershipInfo`.
- **`app/api/v1/auth.py`** — Four endpoints:
  - `POST /v1/auth/login` — verifies email/password via Argon2, issues access + refresh tokens.
  - `POST /v1/auth/refresh` — validates refresh token (checks `type: "refresh"`), issues new token pair.
  - `POST /v1/auth/logout` — stateless 200 OK.
  - `GET /v1/auth/me` — returns user identity + memberships (resolves org name and role name via joins).

### Key decisions
- `is_super_admin` is **never** placed in the JWT. Resolved via DB query in `get_current_user`. Verified: decoded access token contains only `sub` and `exp`.
- `get_current_user` queries the `users` table on every request and rejects if `is_active = False` with `401 Unauthorized`.
- The `decode_token` function raises `HTTPException(401)` directly, so it's used both in `get_current_user` and the `/refresh` endpoint.
- Refresh tokens include a `type: "refresh"` claim so access tokens (which lack this claim) cannot be used to refresh.
- `python-jose[cryptography]` chosen for JWT; `passlib[argon2]` for Argon2.

### Verification results
- Login returns access + refresh tokens.
- Decoded access token JWT payload: `{'sub': '1', 'exp': ...}` — only `sub` and `exp`, no `is_super_admin`/roles/permissions.
- `/me` with valid token returns user details including `is_super_admin: true` (resolved from DB).
- `/me` without token → `401`.
- `/me` with invalid token → `401`.
- `/refresh` accepts a valid refresh token and returns new tokens.
- `/logout` returns `{"message": "Logged out successfully"}`.

## BE-104 — Implement Organizations & Users APIs

**Status:** Completed

### What was implemented
- **`app/schemas/organizations.py`** — `OrganizationCreate`, `OrganizationUpdate`, `OrganizationResponse`, `PaginatedResponse[T]` generic wrapper.
- **`app/core/authorization.py`** — `require_super_admin` FastAPI dependency (wraps `get_current_user`, returns `403 Forbidden` if `is_super_admin` is False).
- **`app/services/organization_service.py`** — Business logic layer with cursor-based pagination (`list_organizations`), slug generation with collision dedup, and full CRUD operations.
- **`app/api/v1/organizations.py`** — Five endpoints, all guarded by `require_super_admin` at the router level:
  - `GET /v1/organizations` — cursor-paginated list.
  - `POST /v1/organizations` — create with auto-generated slug.
  - `GET /v1/organizations/{id}` — get by ID.
  - `PUT /v1/organizations/{id}` — update name/slug/description.
  - `DELETE /v1/organizations/{id}` — hard delete.

### Key decisions
- **403 vs 404 for super admin check:** The Architecture.md Section 9.3 says "all authorization failures return 404" for *tenant isolation* failures. The super admin check on `/v1/organizations` is a global admin guard, not a tenant-scoped resource check, so 403 is appropriate here.
- **Cursor pagination strategy:** Uses opaque integer cursor (the `id` of the last item). Query: `WHERE id > :cursor ORDER BY id ASC LIMIT :limit`. The `next_cursor` in the response is `str(items[-1].id)` when `len(items) == limit`, else `None`.
- **Slug generation:** Simple regex-based slugify (`re.sub(r"[^a-z0-9 -]", "", text).replace(" ", "-")`). If the slug already exists, appends `-1`, `-2`, etc. until unique.

### Verification results
- `POST /v1/organizations` with `{"name": "Acme Corp"}` → 201, slug `acme-corp`.
- `POST /v1/organizations` with explicit slug `{"name": "Globex Inc", "slug": "globex"}` → slug `globex`.
- `GET /v1/organizations?limit=1` → 1 item + `next_cursor: "1"`. `?limit=1&cursor=1` → next item + `next_cursor: "2"`.
- `GET /v1/organizations/2` → returns Globex Inc.
- `PUT /v1/organizations/1` with `{"name":"Acme Corp Updated"}` → slug auto-updated to `acme-corp-updated`.
- `DELETE /v1/organizations/3` → 204. Subsequent `GET /3` → 404.
- Non-admin user `GET /v1/organizations` → 403.

## BE-105 — Implement Memberships API

**Status:** Completed

### What was implemented
- **`app/schemas/memberships.py`** — `MembershipCreate` (user_id, role_id), `MembershipUpdate` (role_id, status with regex validation), `MembershipResponse`.
- **`app/core/authorization.py`** — Two new dependencies:
  - `verify_org_access`: allows any `ACTIVE` member (or super admin) to read org-scoped resources.
  - `verify_org_admin`: requires `role.rank == 1` (Org Admin) or super admin for mutating endpoints. Both return 404 if the user has no valid membership.
- **`app/services/membership_service.py`** — `upsert_member` (query by user_id+org_id, update if exists else insert), `update_member` (role_id/status changes with rank check), `list_members`, `get_member`, `delete_member`.
- **`app/api/v1/memberships.py`** — Five endpoints under `/v1/organizations/{org_id}/members`:
  - `GET` — list members (any active member of the org).
  - `POST` — assign a role to a user (upsert + rank check).
  - `GET /{member_id}` — get single member.
  - `PUT /{member_id}` — update role_id and/or status.
  - `DELETE /{member_id}` — remove membership.

### Key decisions
- **verify_org_admin** returns `tuple[User, int]` so the route handler can access the caller's user object and their rank.
- **Rank comparison:** `caller_rank >= target_role.rank` → 404. Only strict `<` is allowed (e.g., rank 1 can assign rank 2, but not rank 1).
- **Upsert implementation:** Query by `(user_id, organization_id)` ignoring status. If a row exists, update its `role_id` and set `status = 'ACTIVE'`. If not, insert a new row. This avoids violating the partial unique index.
- **PUT accepts both role_id and/or status** per Architecture.md Section 12 ("PUT allows updating role_id or status").

### Verification results
- Super Admin assigns user 2 (Org Admin role, rank 1) in org 1 → 201.
- User 2 (Org Admin, rank 1) assigns user 3 (Editor role, rank 2) → 201.
- User 2 tries to assign Org Admin role (rank 1 = same rank) → 404.
- User 2 assigns user 3 again (Editor) → updates existing row (same id=2, no duplicate) → 200.
- Super Admin suspends member → PUT with `{"status": "SUSPENDED"}` → 200.
- Super Admin deletes member → 204.
- Non-member accesses org 2 members → 404.
- Super Admin lists members → returns both members.

## BE-109 — Permission Resolution & Sync Cache Invalidation

**Status:** Completed

### What was implemented
- **`app/core/cache.py`** — Added `permissions_cache_key(org_id, role_id)` → `perms:org:{org_id}:role:{role_id}`.
- **`app/core/authorization.py`** — Refactored permission resolution:
  - `_compute_permissions_from_db` — sync helper that queries DB for role defaults + org overrides.
  - `resolve_permissions` — async, checks Redis cache first. Cache hit → return. Cache miss → call `_compute_permissions_from_db`, populate Redis with 30s TTL, return.
  - `authorize` — now async (calls `await resolve_permissions`).
  - `require_permission` — inner dependency is now async.
- **`app/schemas/permissions.py`** — New schemas: `PermissionOverride` (permission_id, allowed), `PermissionOverrideResponse` (permission_id, permission_name, allowed, source).
- **`app/api/v1/permissions.py`** — Two endpoints (both guarded by `require_permission("permission.manage")`):
  - `GET /v1/organizations/{org_id}/roles/{role_id}/permissions` — returns all permissions for a role in an org, annotated with `source: "default" | "override"` and the `allowed` value.
  - `PUT /v1/organizations/{org_id}/roles/{role_id}/permissions` — replaces all overrides. Deletes existing `OrganizationRolePermission` rows for the org/role, inserts the new ones, commits, then invalidates Redis cache **after** commit.

### Key decisions
- **Strict post-commit invalidation:** The PUT endpoint calls `db.commit()` first. If it succeeds, `delete_cache` runs. If commit fails, the exception propagates and cache deletion is never reached. If cache deletion itself fails, the exception is logged but the HTTP request succeeds (30s TTL safety net).
- **Async authorization flow:** `resolve_permissions` is async to support `await` on Redis calls. `authorize` and the `require_permission` dependency are async too. FastAPI handles async dependencies seamlessly, even when the inner DB queries are sync.
- **`_compute_permissions_from_db`** exposed as a public module-level function so the `permissions.py` GET endpoint can reuse it for the "defaults" computation without triggering cache read/write.
- **30s TTL** on permission cache keys — short enough to act as a safety net if invalidation fails, long enough to provide meaningful reduction in DB queries.

**Status:** Completed

### What was implemented

- **`app/services/audit_service.py`** — `log_action(db, actor_id, org_id, action, entity_type, entity_id, before, after)` appends an `AuditLog` to the DB session.
- **Membership service integration** — `upsert_member`, `update_member`, `delete_member` accept `actor_id` (via `caller.id`) and call `log_action` before `db.commit()` — same transaction.
- **Permissions PUT integration** — `put_role_permissions` captures old overrides as `before`, new overrides as `after`, calls `log_action` before `db.commit()`.
- **`app/api/v1/audit.py`** — Two endpoints:
  - `GET /v1/organizations/{org_id}/audit-logs` — requires `audit.read` permission, returns org-scoped logs descending by `created_at`.
  - `GET /v1/audit-logs?organization_id={id}` — Super Admin only, returns all logs optionally filtered by org.
- **`app/seed.py`** — Added `permission.manage` and `audit.read` permissions; Org Admin gets all 10 permissions.

### Key decisions
- **Same-transaction audit entries:** `log_action` calls `db.add(entry)` but *does not commit*. The caller (service layer) commits, ensuring the audit entry is atomically persisted with the mutation. If the mutation fails mid-flight, the audit entry is also rolled back.
- **`entity_type` values:** `"membership"` for membership CRUD, `"role_permissions"` for permission overrides (since one PUT replaces all overrides for a role).
- **Before/after capture:** For upserts, `before=None` on create, `before=existing_state` on update. For deletes, `after=None`. For permissions, `before` and `after` are dicts of `{permission_id: allowed}`.
- **JSONB handling:** Python dicts are passed directly to the mapped column; SQLAlchemy + psycopg2 handle the `json.dumps`/`json.loads` automatically.
- **Added `permission.manage` and `audit.read`** to the seed so the permissions endpoint works for non-super-admin users and audit endpoints have an appropriate guard.
